# 实验范式仓库整理方案

> 执行状态（2026-07-23）：代码拆分、公共模块提取、CLI 兼容层、仓库内新闻
> 刺激副本、相对默认路径、独立新闻文档和结构回归测试均已完成。既有刺激和音频
> 未删除；真实全屏实验仍需在目标实验电脑上手工验收。
>
> 自动验收：仓库 manifest 测试现已覆盖两套主要患者流程——v4 闭锁范式和
> 新闻放松范式。旧英文/中文音频目录仍作为资产保留，但不再是当前默认输入。

## 1. 整理目标

本次整理的目标不是重写现有范式，而是在保持现有实验行为、命令行参数、
音频资产和时间戳字段兼容的前提下，降低后续维护和增加新范式的成本。

整理完成后应满足：

1. `src/` 是所有范式实现、参数默认值和输入验证的唯一来源。
2. `scripts/` 只保留仓库检出状态下的轻量启动入口。
3. 每个范式拥有独立的实现文件和命令行参数文件。
4. 公共的显示、音频、计时、输入解析和结果保存逻辑集中复用。
5. 刺激文件、生成音频、manifest 和实验结果具有统一命名规则。
6. 已有启动方式继续可用，不要求实验人员临时修改操作习惯。
7. 整理过程不改动既有实验时序和时间戳字段含义。

## 2. 当前主要问题

### 2.1 实现文件过于集中

`src/experiment_paradigm/paradigms.py` 同时包含通用句子、闭锁患者句子阅读、
单词阅读、听力和新闻放松范式。文件过长，不同范式的绘图和时序代码容易
互相影响。

### 2.2 命令行参数过于集中

`src/experiment_paradigm/cli.py` 同时管理所有范式。随着参数增加，查找默认值、
理解参数作用和测试单个范式都变得困难。

### 2.3 公共能力与范式逻辑交织

下列能力目前分散在范式类中：

- Pygame 初始化与退出；
- 中文字体选择和文字布局；
- 灰色十字、红色方块等公共视觉元素；
- 音频 manifest 校验与预加载；
- 音频播放和时间戳记录；
- 随机时长范围验证；
- CSV/JSON 结果保存。

这些能力应当由公共模块提供，具体范式只描述自己的试次流程。

### 2.4 日期和机器相关路径

新闻范式当前使用特定日期的外部绝对路径作为默认输入。该路径适合一次实验，
但不适合长期作为包级默认值，也不方便迁移到其他电脑。

### 2.5 资产命名缺少统一约定

句子音频已经存在多个版本，新闻音频按日期存放。虽然目前可以辨认，但尚未
形成统一的刺激文件、音频目录和 manifest 配对规则。

### 2.6 工作区修改较多

当前存在多轮需求累积的代码、文档、刺激和音频修改。正式整理前应先确认哪些
内容需要纳入版本控制，避免在大规模移动文件时混入无关变化。

## 3. `src/` 与 `scripts/` 的边界

### 3.1 `src/` 负责的内容

`src/experiment_paradigm/` 是维护代码的唯一来源，应当包含：

- 范式类和试次流程；
- Pygame 绘制与布局；
- 音频生成、校验、预加载和播放；
- 参数定义、默认值和输入检查；
- 刺激文件解析；
- 随机化和重复逻辑；
- 时间戳与结果保存；
- 可以被测试或复用的公共函数。

修改范式行为时，只修改 `src/` 中的实现。

### 3.2 `scripts/` 负责的内容

`scripts/` 只提供从仓库根目录直接运行的兼容入口。每个脚本只应：

1. 将仓库的 `src/` 加入导入路径；
2. 导入一个包内入口函数；
3. 在 `if __name__ == "__main__"` 中调用该函数。

`scripts/` 中不应出现：

- 实验默认参数；
- Pygame 绘图；
- 试次时序；
- TTS 逻辑；
- 刺激解析；
- 参数验证；
- 结果保存。

## 5. 各模块职责

### 5.1 `core/base.py`

放置 `BaseParadigm`，负责：

- Pygame 初始化；
- 全屏窗口和时钟；
- 退出事件检查；
- 实验起始时间；
- 统一清理流程。

### 5.2 `core/audio.py`

负责：

- manifest schema 校验；
- 文字与音频顺序校验；
- SHA-256 校验；
- 音频预加载；
- 分段音频依次播放；
- 音频 onset、offset 和 segment 事件记录。

该模块不决定音频在一个 trial 的哪个阶段播放。

### 5.3 `core/display.py`

负责可复用视觉元素：

- 中文字体选择；
- 自动字号计算；
- 单行和多行文字布局；
- 红色、绿色方块；
- 灰色注视十字；
- 黑色背景；
- 进度条绘制。

具体范式决定何时调用这些元素。

### 5.4 `core/timing.py`

负责：

- 非负时长验证；
- 最小值和最大值范围验证；
- 均匀随机时长生成；
- 可退出的定时显示循环。

所有时间单位继续使用秒。

### 5.5 `core/results.py`

负责：

- CSV 和 JSON 保存；
- 输出目录创建；
- 文件名时间戳；
- 嵌套字段在 CSV 中的稳定序列化。

现有字段名称和含义不得因拆分而改变。

### 5.6 `paradigms/`

每个文件只实现一个范式或一组紧密相关的范式：

- `sentence.py`：通用句子范式；
- `locked_in_reading.py`：闭锁患者中文句子阅读范式；
- `relaxing_news.py`：新闻放松朗读范式；
- `reading.py`：单词阅读范式；
- `listening.py`：独立听力范式。

范式文件主要描述 trial 的阶段顺序、画面状态和记录字段，不重复实现公共工具。

### 5.7 `commands/`

每个命令文件负责：

- 创建 `ArgumentParser`；
- 按功能分组参数；
- 保存该范式的默认值；
- 将参数传给对应范式；
- 提供安装后的 console entry point。

### 5.8 `stimuli/`

包内 `stimuli/` 模块负责解析，仓库根目录的 `stimuli/` 负责保存实际输入数据。

解析模块包括：

- 普通 UTF-8 非空行；
- Markdown 新闻表格标题列；
- 中文逐字 TTS 单元；
- 整句 TTS 单元。

## 6. 数据与资产规范

### 6.1 刺激文件

建议使用：

```text
stimuli/
├── locked_in/
│   ├── yan_jiangyi_v1.txt
│   ├── yan_jiangyi_v2.txt
│   └── yan_jiangyi_v3.txt
└── news/
    └── 2026_07_23.md
```

刺激文件是文字内容的权威来源。不要仅依赖 manifest 中保存的文字。

### 6.2 音频资产

建议与刺激版本一一对应：

```text
assets/
├── sentence_audio/
│   ├── yan_jiangyi_v1_slow/
│   ├── yan_jiangyi_v2_slow/
│   └── yan_jiangyi_v3_slow/
└── news_audio/
    └── 2026_07_23/
```

每个音频目录包含：

- `manifest.json`；
- 按稳定编号命名的 MP3；
- manifest 中的 TTS 语音、语速、音调、时长和 SHA-256。

### 6.3 新闻输入路径

不在包内写死某台电脑的绝对路径。建议采取以下方式之一：

1. 将正式使用的新闻文件复制到 `stimuli/news/`，命令使用仓库相对路径；
2. 保留外部新闻文件，但每次通过 `--news` 明确传入；
3. 增加可选的实验配置文件，记录新闻路径和 manifest 路径。

正式整理时推荐第 1 种方式，最容易复现。

### 6.4 实验结果

继续将运行结果写入 `timestamp/`，并保持：

- 新生成结果默认不纳入版本控制；
- 已存在的示例结果不删除、不改写；
- CSV 和 JSON 使用相同的运行标识；
- 所有随机计划时长和实际时长均保留。

## 7. 向后兼容要求

整理后以下入口必须继续工作：

```powershell

python scripts/run_sentence_audio_zh.py
python scripts/run_relaxing_news.py
python scripts/run_reading.py
python scripts/run_listening.py
```

安装后的命令也必须保持：

```text
generate-sentence-audio
generate-news-audio
run-sentence-audio
run-sentence-audio-zh
run-locked-in-sentence-reading
run-relaxing-news
run-reading
run-listening
```

兼容要求还包括：

- 原命令行参数名称不改变；
- 原默认时序不改变；
- manifest schema 1 和 schema 2 继续可读；
- 原时间戳字段名称不改变；
- 原有音频文件无需重新生成；
- 原有刺激顺序、重复和随机逻辑不改变。

可以在旧模块中保留短期导入别名，例如从新的范式模块重新导出类，以避免外部
代码立刻失效。

## 8. 分阶段实施计划

### 阶段 0：整理前冻结与确认

1. 查看当前 Git 工作区。
2. 区分代码修改、用户刺激、生成音频和实验输出。
3. 确认需要保留的 `yan_jiangyi` 各版本和新闻音频。
4. 为当前可运行状态建立一次明确提交或备份点。
5. 记录当前相关测试结果和命令行帮助输出。

完成标准：可以明确回退到整理前的可运行状态。

### 阶段 1：拆分范式文件

1. 创建 `paradigms/` 包。
2. 逐个移动范式，每次只移动一个类。
3. 优先移动依赖最少的 `reading.py` 和 `listening.py`。
4. 再移动 `relaxing_news.py`。
5. 最后移动通用句子和闭锁患者范式。
6. 在旧 `paradigms.py` 中保留兼容导入，暂不删除。

完成标准：所有原入口和测试保持通过，范式行为未改变。

### 阶段 2：提取音频公共逻辑

1. 移动 manifest 校验。
2. 移动音频预加载。
3. 移动分段音频播放。
4. 保持原时间戳字段不变。
5. 使用现有 schema 1、schema 2 和实际新闻 manifest 做回归测试。

完成标准：句子、闭锁患者和新闻范式共用同一套音频组件。

### 阶段 3：提取显示和计时公共逻辑

1. 提取字体加载。
2. 提取灰色十字、方块和黑屏绘制。
3. 提取可退出定时循环。
4. 保留各范式自己的尺寸和颜色参数。
5. 对关键像素位置和时序字段增加测试。

完成标准：视觉公共元素不再在多个范式中复制。

### 阶段 4：拆分命令行模块

1. 为每个范式建立独立参数解析函数。
2. 保留当前参数分组和帮助文字。
3. 更新 `pyproject.toml` 的 console entry points。
4. 保留旧 `cli.py` 作为兼容转发层。
5. 检查每个 `-h` 输出。

完成标准：修改一个范式的参数不会影响其他范式的 CLI 文件。

### 阶段 5：规范刺激和资产

1. 统一 `yan_jiangyi` 文件名，补齐 `.txt` 扩展名。
2. 将新闻输入整理到 `stimuli/news/`，或明确要求 `--news`。
3. 确认每个刺激文件对应唯一音频目录。
4. 检查 manifest 中的相对路径、文字、顺序和校验值。
5. 不移动或删除未经确认的已有音频。

完成标准：仅看刺激路径即可确定应使用哪个 manifest。

### 阶段 6：文档与清理

1. 为每个范式建立独立运行文档。
2. README 只保留项目概览和链接。
3. 删除已经无人引用的兼容代码，但保留脚本入口。
4. 更新目录结构说明。
5. 检查 Git 状态，确保没有意外生成的结果文件。

完成标准：新使用者可以从 README 找到对应范式，并通过一条生成命令和一条
运行命令完成操作。

## 9. 测试与验收

### 9.1 自动检查

每次阶段性修改后运行：

```powershell
python -c "import ast, pathlib; [ast.parse(p.read_text(encoding='utf-8')) for p in pathlib.Path('src').rglob('*.py')]"
python -m unittest tests.test_cli tests.test_sentence_audio tests.test_news
git diff --check
```

还应增加或保留以下测试：

- 参数默认值；
- 参数帮助分组；
- Markdown 新闻提取；
- manifest 文字与顺序校验；
- SHA-256 错误拒绝；
- schema 1 和 schema 2 兼容；
- 逐字音频播放顺序；
- 循环和随机顺序；
- 红方块始终为红色；
- 灰色十字位置和大小；
- 新闻长文本自动换行和缩小；
- 结果字段名称不变。

### 9.2 手工检查

自动测试不得启动真实全屏范式。完成一个阶段后，在实验电脑上分别手工检查：

1. 闭锁患者句子范式；
2. 新闻放松范式；
3. 单词阅读范式；
4. 独立听力范式；
5. `Esc` 和鼠标退出；
6. 音频音量、画面位置和全屏分辨率；
7. CSV/JSON 输出。

### 9.3 验收原则

整理工作只有在以下条件全部满足时才算完成：

- 所有相关自动测试通过；
- 原启动命令继续可用；
- 原音频可以直接加载；
- 关键默认参数未变化；
- 关键时间戳字段未变化；
- 没有删除或重写用户刺激和实验资产；
- 至少在目标实验电脑上完成一次手工运行检查。

## 10. 风险与控制

### 10.1 大规模移动导致导入失败

控制方式：一次只移动一个范式；旧模块保留兼容导入；每一步运行测试。

### 10.2 时间戳含义被无意改变

控制方式：先记录现有字段，再提取公共逻辑；使用字段集合和事件顺序测试。

### 10.3 音频与刺激错配

控制方式：始终校验文字、顺序、文件存在性和 SHA-256；资产移动后重新验证
manifest，但不重新合成音频。

### 10.4 误删生成资产

控制方式：整理前列出所有受版本控制和未受版本控制的资产；未经明确确认不执行
删除、覆盖或批量移动。

### 10.5 一次重构范围过大

控制方式：严格按阶段提交。任何阶段出现行为变化时，先修复或回退，不继续叠加
下一阶段。

## 11. 推荐优先级

建议按以下优先级执行：

1. 先建立整理前提交或备份点；
2. 拆分 `paradigms.py`；
3. 提取音频公共逻辑；
4. 提取显示和计时公共逻辑；
5. 拆分 `cli.py`；
6. 规范刺激与音频目录；
7. 最后精简 README 和兼容层。

不建议一开始就批量重命名或移动全部刺激和音频。代码拆分更容易通过测试验证，
而资产移动需要额外人工确认。

## 12. 本方案不包含的操作

本方案本身不授权执行以下操作：

- 删除或覆盖已有刺激；
- 删除或重新生成已有音频；
- 修改实验默认时序；
- 修改时间戳字段名称；
- 提交、推送或创建分支；
- 启动真实全屏实验。

这些操作应在具体实施阶段逐项确认。
